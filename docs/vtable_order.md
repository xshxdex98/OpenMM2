# Virtual method slot order

Generated by `tools/vtable_order.py`. Data: `data/vtable_order.json`.
Consumed by `tools/asm_vtables.py`; `docs/vtables.md` is how a polymorphic class is
actually handed over to C++.

## Why this matters

A C++ compiler assigns vtable slots in **declaration order**. `tools/genheaders.py` sorts
methods alphabetically after the constructor and destructor - correct for readability, and
catastrophic for a polymorphic class. The moment such a class is reimplemented, the
compiler emits a vtable whose virtuals are in alphabetical order while every piece of
original 1999 code still calls through *slot indices* taken from the 1999 declaration
order. `Update` gets called when the binary meant `Reset`. Same signature, same arity, no
link error, no crash at the call site - the game just behaves as if it had gone insane.

This document records the real order, read out of `.rdata`.

## Method

For each `??_7...@@6B...` symbol, `.rdata` is walked one dword at a time. Any value inside
`.text` is a slot; the first value outside it ends the table, and the next vftable symbol
is a hard ceiling because vftables sit back to back. An entry with no symbol is still a
real slot - a pure virtual resolves to `__purecall`, and thunks are not always named - so
only the section test terminates.

Each address is resolved against `data/symbols.json` (authoritative) and classified
against the base class's own table:

| kind | meaning |
|---|---|
| `inherited` | the base's table holds the identical pointer at this index |
| `override` | the base's table holds a different pointer at this index |
| `new` | this index is past the end of the base's table |
| `pure` | the slot points at `__purecall` |
| `thunk` | the slot points at an `[thunk]:` adjustor or vcall thunk |
| `unnamed` | a real code pointer `midtown2.map` never named |

An address that falls *inside* a named symbol rather than at its start is **not** that
symbol. The map's `size` is the distance to the next named symbol, so a function the map
omits is swallowed by its predecessor's extent. Such slots are `unnamed`, with the
containing symbol kept only as provenance (`inside_symbol`). Resolving them by containment
reported `mmMultiCircuit` slot 0 as an override of `GameMessage`; it is the deleting
destructor.

> `midtown2.map`'s `Rva+Base` column is 0x308 too high for `.rdata`. `data/symbols.json`
> already carries the corrected `rva` (raw value kept as `map_rva`); this tool reads `rva`
> only. Using `map_rva` here lands every lookup on a neighbouring table.

## The prefix property

A base's vtable must be a prefix of its derived class's: the derived table is at least as
long, and at every index the base also has, the derived table holds either the identical
pointer or a function of the same name.

**This is checked slot by slot, not by length.** The length-only version passes 279 of 279
and proves nothing: it cannot see a table paired with the wrong base, which is exactly the
failure it exists to catch.

Result: **277 of 279** base/derived pairs hold.

| class | base | first differences |
|---|---|---|
| `mmMultiCircuit` | `mmGameMulti` | slot 0 holds `?`, base holds `~dtor` |
| `vehSuspension` | `asNode` | slot 6 holds `Copy`, base holds `FileIO` |

Both are understood, and neither is a slot-order error:

- **`mmMultiCircuit` slot 0** is the only code pointer in the whole of `.rdata` that
  `midtown2.map` does not name. It is the deleting destructor; every other class has
  one at slot 0 and this one was simply left out of the map. Declare
  `virtual ~mmMultiCircuit()` and the slot fills itself.
- **`vehSuspension` slot 6** holds `?Copy@vehSuspension@@QAEXABV1@@Z`, which is not
  virtual and therefore cannot be in a vtable. There is no `?FileIO@vehSuspension@@`
  symbol at all. This is **identical COMDAT folding**: `vehSuspension::FileIO` and
  `vehSuspension::Copy` compiled to the same bytes, the linker kept one copy, and the
  map kept one name. The slot is `asNode::FileIO` overridden - declare it as such.

Folding is worth understanding because it is the one way a slot can carry a wrong name
*silently*. Where the base has the same slot, the prefix check above catches it, as it
did here. Where the slot is new, nothing can: the address is right, the name may not
be. Read the pseudocode before trusting a `new` slot's name.

## Classes whose own virtuals are not all in their own table

If a class declares `virtual void Reset()`, then `?Reset@Cls@@...` must occupy a slot in
`Cls`'s own table. Where several do not, the table carrying that name is not that
class's table.

| class | slots | own virtuals absent |
|---|--:|---|
| `dgUnhitBangerInstance` | 28 | Impact, ImpactCB, Init, Reset |
| `lvlInstance` | 26 | DrawPhysics |

**`??_7dgUnhitBangerInstance@@6B@` is a mislabelled symbol. Do not port that class from
its own table.** The evidence is conclusive:

- The table under that name holds `?Reset@lvlInstance@@` at slot 0 and
  `?Init@lvlInstance@@` at slot 17, while **every one of the eleven classes that derive
  from `dgUnhitBangerInstance`** holds `?Reset@dgUnhitBangerInstance@@` and
  `?Init@dgUnhitBangerInstance@@` at those indices. A base cannot fail to contain an
  override that all its descendants inherit.
- It is 28 slots; `dgUnhitMtxBangerInstance` and `dgUnhitYBangerInstance` are 30, and
  the two extra slots hold `?Impact@dgUnhitBangerInstance@@` and
  `?ImpactCB@dgUnhitBangerInstance@@` - virtuals a derived class cannot introduce.
- It matches MM2Hook's `dgBangerInstance` `_vtbl` on 26 of 28 slots, and
  `dgBangerInstance` is one of the classes MM2Hook describes that emits no table.

So the 28-slot table at that address is `dgBangerInstance`'s. The real chain is
`lvlInstance` (26) -> `dgBangerInstance` (28, adds `ComputeLod` and a *const*
`SetupGfxLights`) -> `dgUnhitBangerInstance` (30, adds `Impact`, `ImpactCB`). Take
`dgUnhitBangerInstance`'s order from `dgUnhitMtxBangerInstance`'s table instead.

**`lvlInstance::DrawPhysics` occupies no slot in any of the 340 tables.** It is a
public virtual with 576 bytes of real code, and nothing dispatches to it. Declaring it
`virtual` on the C++ side would add a 27th slot to `lvlInstance` and shift every one of
its descendants. Declare it non-virtual, or leave it out.

## Multiple inheritance

A class with more than one vftable symbol has more than one vtable, one per base
subobject, and the secondary tables are reached through `[thunk]:` adjustors.

None of the five has an unqualified `??_7C@@6B@`, so the primary table has to be picked.
**It is the one with no adjustor thunk in it**, not the one at the lower address: a
secondary table is entered with a `this` that has to be corrected first, so MSVC fills its
overridden slots with `[thunk]: ... adjustor{N}` stubs, and the primary never needs one.
Picking by address put `vehTrailer`'s asNode subobject first and made MM2Hook look like it
disagreed on nine consecutive slots; against the right table it agrees on all of them.

| class | primary | secondary |
|---|---|---|
| `CFileStream` | `??_7CFileStream@@6BIStream@@@` (14 slots) | `??_7CFileStream@@6BIDirectMusicGetLoader@@@` (4 slots, for `IDirectMusicGetLoader`) |
| `CMemStream` | `??_7CMemStream@@6BIStream@@@` (14 slots) | `??_7CMemStream@@6BIDirectMusicGetLoader@@@` (4 slots, for `IDirectMusicGetLoader`) |
| `dgPhysManager` | `??_7dgPhysManager@@6BphPhysicsManager@@@` (9 slots) | `??_7dgPhysManager@@6BasCullable@@@` (2 slots, for `asCullable`) |

## Cross-check against MM2Hook

`data/mm2types.json` carries MM2Hook's `_vtbl` structs, an independent source that names
virtual slots in order - **2287 slots across 145 classes**. Comparing its name for slot *i*
with the name the map gives the function actually sitting at slot *i*:

| | |
|---|--:|
| classes MM2Hook describes | 145 |
| ...with an emitted table to compare against | 136 |
| slots compared | 2158 |
| name matches | 2055 |
| binary says `__purecall`, MM2Hook names the pure virtual | 92 |
| MM2Hook names a slot past the end of the emitted table | 2 |
| genuine name disagreements | 9 |

**Agreement on slot order: 2147/2158 = 99.5%.**

A `__purecall` slot is counted as agreeing because it *is* agreement about order: MM2Hook
names the pure virtual declared at that index and the binary cannot, since a pure virtual
has no function to point at. Name-for-name, ignoring that, the figure is 2055/2158 = 95.2%.

MM2Hook describes 9 classes that emit no vftable of their own - nothing ever
instantiates them, so the compiler never wrote a table. Their slot counts still matter,
because they are where a derived class's own virtuals start, and MM2Hook is the only
source for them: `LvlInstanceLuaIterator`, `aiRouteRacer`, `asCullable`, `datMultiTokenizer`, `dgBangerInstance`, `luaNode`, `lvlLevelBound`, `mcHookman`, `vehWeelCheap`.

The pattern is one-directional: MM2Hook stops short. Its `_vtbl` structs are
hand-maintained and were only ever filled in as far as somebody needed, which is why
the three tokenizers are described by a single slot against a 19-slot table. The
binary's length is the emitted table, bounded by the next vftable symbol, and it is
what the compiler will have to match.

`lvlFixedRotY` and `lvlLandmark` are the only two where MM2Hook is *longer*, and both
are the same error: it lists `IsVisible` a second time at slot 26, where the emitted
table ends at 26 slots with the next vftable symbol beginning at the very next dword.
`IsVisible` is at slot 2.

Eleven rows, four causes, and **the binary is right in ten of them**:

- **The tokenizers.** MM2Hook's `datAsciiTokenizer`, `datBinTokenizer` and
  `datBaseTokenizer` `_vtbl` structs each contain exactly one entry against a 19-slot
  table. `?Put@datBaseTokenizer@@UAE_ND@Z` is real, and it is at slot **16**.
- **The bangers.** MM2Hook's `dgBangerInstance` omits `ComputeLod` and the *const*
  `SetupGfxLights` - a second virtual of that name, `UBE` rather than `UAE` - so every
  slot it lists after 25 is two too low. This is precisely the silent failure this file
  exists to prevent, present in the cross-check source itself, which is the argument
  for reading the order out of `.rdata` rather than trusting any hand-written list.
- **`lvlFixedRotY` / `lvlLandmark` slot 26**: a duplicated `IsVisible`, see above.
- **`vehSuspension` slot 6**: identical COMDAT folding, see the prefix section. Here
  MM2Hook is right and the map's name is the artefact - the slot is `FileIO`.
